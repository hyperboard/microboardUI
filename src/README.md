## Boards Database

### Store each board in a separate table

Now we a database where we dynamically create tables for each board.

To store events of a table we create a sql table with 3 columns:

1. Server Event Id (integer autoincrement),
2. Client Event Id (string) and
3. Event Body (JSON)

Example:

**Board Events Table**

| Server Event Id (integer autoincrement) | Client Event Id (string) | Event Body (JSON) |
| --------------------------------------- | ------------------------ | ----------------- |
| 1                                       | "1:1"                    | "Add Shape"       |
| 2                                       | "2:1"                    | "Add Text"        |
| 3                                       | "1:2"                    | "Translate Shape" |

But this has following downsides:

1. We have to write dynamic sql to create the table. (But we already done that.)
2. We could reach the limit of files in a directory.

### Store all boards in a single table

We could store all the boards in a single table.

To store events of a table we create a sql table with 4 columns:

1. Server Event Id (integer autoincrement),
2. Client Event Id (string),
3. Board Id (string) and
4. Event Body (JSON)

Example:

**Boards Events Table**

| Server Event Id (integer autoincrement) | Client Event Id (string) | Board Id (string) | Event Body (JSON) |
| --------------------------------------- | ------------------------ | ----------------- | ----------------- |
| 1                                       | "1:1"                    | "1"               | "Add Shape"       |
| 2                                       | "2:1"                    | "1"               | "Add Text"        |
| 3                                       | "1:2"                    | "1"               | "Translate Shape" |
| 4                                       | "1:1"                    | "2"               | "Add Shape"       |

But this has following downsides:

1. it makes server event id order events from different boards. (we can fix it if we set the server event id ourselves. Or we do not need to fix it because the logical order of events for each table stays the same.)
2. it makes it slower to get all events for a board. (we can fix it if we add a index on the board id column.)

### Store all boards in a partitioned table

We could store all the boards in a partitioned table. (This is the best solution.)

We could partition the table by the board id.

## SSO

Cross-origin authentication with OpenID Connect (OIDC) Single Sign-On (SSO) refers to the capability of authenticating users across multiple domains or origins using the OIDC protocol.

In a typical scenario, when a user attempts to log in to an application in a different domain, the OIDC SSO process allows the user's authentication to be seamlessly shared between the domains. This eliminates the need for the user to authenticate individually for each domain.

Here's a step-by-step approach to cross-origin authentication with OIDC SSO:

1. Domain Setup:

    - Configure the OIDC server (Identity Provider) to handle authentication and issue access tokens.
    - Set up the necessary client applications (Relying Parties) with the appropriate redirect URIs and client IDs.

2. Login Flow:

    - The user visits a client application (origin A) that initiates the OIDC authentication flow.
    - The client application redirects the user to the OIDC server, passing the necessary client ID and redirect URI.
    - The user is presented with a login page hosted by the OIDC server.
    - The user enters their credentials and submits the login form.
    - The OIDC server validates the credentials and issues an ID token and access token.
    - The OID C server redirects the user back to the client application (origin A) with the ID token and access token.

3. Token Verification:

    - The client application (origin A) receives the ID token and access token.
    - The client application verifies the ID token's signature and performs necessary validation checks (e.g., expiration, audience, issuer, etc.).
    - If the ID token is valid, the client application can extract user information from it and authenticate the user locally.

4. Cross-Origin Authentication:

    - The same user now visits another client application (origin B) within a different domain.
    - The client application (origin B) also follows the OIDC authentication flow described in steps 2 and 3, redirecting the user to the OIDC server and receiving ID token and access token.
    - However, instead of asking the user to log in again, the OIDC server recognizes that the user has already authenticated at origin A through the same server.
    - The OIDC server then redirects the user back to the client application (origin B) with a new ID token and access token.

5. Token Verification (in origin B):
    - The client application (origin B) verifies the new ID token's signature and performs the necessary validation checks.
    - If the ID token is valid, the client application can extract user information from it and authenticate the user locally.

By implementing cross-origin authentication with OIDC SSO, users can seamlessly authenticate across multiple applications or domains without the need to log in multiple times. This improves user experience and reduces the burden of managing separate authentication systems for each domain.
